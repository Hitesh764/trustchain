# TrustChain — Hosting Guide (Phase 11)

Like Phase 5's Sepolia deployment, this needs accounts on external services
only you can create — I can't sign up for Vercel/Render/MongoDB Atlas on your
behalf. What's done here: the codebase is production-ready (build configs,
security headers, SPA routing config), and a real production build has been
built, served, and verified in a browser end-to-end (see "Verified" below).

## Overview

```
Frontend (static build) ──► Vercel or Netlify
Backend (Node process)  ──► Render or Railway
Database                ──► MongoDB Atlas (free tier)
Blockchain               ──► Sepolia (see docs/DEPLOYMENT.md — already covered)
```

## 1. MongoDB Atlas

1. Create a free M0 cluster at [mongodb.com/cloud/atlas](https://www.mongodb.com/cloud/atlas).
2. Database Access → add a user with a strong password.
3. Network Access → allow access from anywhere (`0.0.0.0/0`) — simplest for a
   college project; Render's outbound IPs aren't static on the free tier.
4. Get the connection string (Drivers → Node.js) and use it as `MONGO_URI` below.

## 2. Backend — Render

`render.yaml` (repo root) defines the service as Infrastructure-as-Code — Render
detects it automatically when you connect the repo ("New +" → "Blueprint").

Required environment variables (Render will prompt for the ones marked
`sync: false` in `render.yaml`):

| Variable | Value |
|---|---|
| `MONGO_URI` | your Atlas connection string |
| `CLIENT_URL` | your deployed frontend's exact origin, e.g. `https://trustchain.vercel.app` (no trailing slash) |
| `SEPOLIA_RPC_URL`, `OPERATOR_PRIVATE_KEY`, `CONTRACT_ADDRESS` | from `docs/DEPLOYMENT.md`, if going live on Sepolia |

`JWT_SECRET` is auto-generated by Render (`generateValue: true`) — don't reuse
the dev one.

**Known limitation, documented rather than silently shipped**: `server/uploads/`
(QR PNGs, counterfeit-report photos) is written to local disk. Render's free
web services have an *ephemeral* filesystem — it's wiped on every redeploy or
restart. For a college project this is an acceptable, disclosed limitation;
QR PNGs regenerate on demand anyway (`getQrPngBuffer` falls back to
`QRCode.toBuffer` if the file's missing), so only uploaded *report photos*
are actually at risk of loss. A real production deployment would move
`server/uploads/` to S3-compatible object storage or Render's paid persistent
disks — out of scope here, but the fix is isolated to `qr.service.js` and
`upload.middleware.js` if it's ever needed.

## 3. Frontend — Vercel

1. Import the repo, set **root directory to `client`**.
2. Vercel auto-detects Vite (`npm run build`, output `dist`) — no other config needed.
3. `vercel.json` (already in `client/`) adds the SPA rewrite every client-side
   route needs — without it, refreshing `/verify/:productId` 404s, since
   there's no `verify` folder on the static host to find.
4. Environment variable: `VITE_API_BASE_URL` = your Render backend's URL + `/api`,
   e.g. `https://trustchain-api.onrender.com/api`.

**Netlify alternative**: `client/public/_redirects` (already present,
`/* /index.html 200`) is Netlify's equivalent SPA-fallback mechanism, copied
into `dist/` automatically by Vite since anything in `public/` ships as-is.

## 4. Production hardening already in place

- `helmet()` — standard security headers (`crossOriginResourcePolicy` relaxed
  so the frontend's separate origin can still `<img>`-load QR PNGs from the API).
- `compression()` — gzips JSON/API responses.
- `morgan("combined")` in production instead of the dev-friendly `"dev"` format.
- Route-level code splitting (`React.lazy` in `App.jsx`) — `html5-qrcode`
  alone was responsible for most of a 604KB single bundle `vite build` warned
  about; splitting it into its own chunk (loaded only on `/scan`) cut the
  main bundle to 178KB (58KB gzipped).
- Rate limiting on auth/verify/report routes (Phase 8).

## Verified

A real production build was built and served locally (`vite build` +
`vite preview`), then driven with a real browser against the real backend:
landing page renders, a deep-link route (`/verify/:productId`) hit directly
(not via client-side navigation) resolves correctly — proving the SPA
rewrite config is actually necessary and actually works — the lazy-loaded
scanner chunk loads on demand, and the 404 page's SPA fallback works. Zero
console errors. This also caught a real, expected interaction: CORS
correctly blocked the preview server's origin until `CLIENT_URL` was updated
to match it, which is exactly the check that will matter once the real
frontend and backend are on different domains.
